### I-194: missing textures matched by texture-table order (proposal, nothing integrated)

The containers store identical files once, so many animation folders of the JP 4.3.1 dump hold only the `.lwf`
while the same bitmaps sit in films, raids, effects, NPCs or other enemies. `deep_donors.py` only accepts a donor
through surviving pieces of the same animation, so animations with no surviving texture were never matched. New
`recon/tools/dedup_match.py` (+ `test_dedup_match.py`): for each incomplete animation, candidate donor LWFs by
exact declared size (the 25 covering most missing sizes plus the 15 whose table is mostly missing sizes, so small
NPC/raid LWFs are not crowded out by films), alignment of the two texture tables by order (`lcs_map` on `(w, h)`),
pick = the donor with the longest contiguous run at that index; known pieces confirm/contradict each donor (content
diff tolerant to rescaled copies); same-size variants (skin/hair/clothes of characters built on one body template)
are resolved by the run, then by colour agreement with trusted table neighbours; earlier visual rejects stay C.
Confidence A (clean donor, long run or unique large size, confirmed), B (aligned, ambiguity resolved), C (donors
disagree, contradicted donor, weak alignment, visual reject).

Results over the 295 incomplete animations (4,582 missing pieces): A 1,508, B 1,248, C 1,277, no source 549.
Whole families that would be complete: 8 with A only (208, 272, 1525, 1541, 1577, 1619, 1624, 1625), 3 with A+B
(240, 1552, 1610), 17 more only with C pieces accepted; 34 families still lack an LWF (`dead` or allies' animations),
37 keep holes. Checked by eye on the rendered rigs: 1625/1624/1619 Cy-Bug family, 266 Gummi Hound (the raid 1010
