### What we knew after the static analysis

- The client takes the base URL from the bootstrap **response**, not from a constant
- Contract: bootstrap → `{maintenance, url, nativeToken}`; session →
  `{nativeSessionId, sharedSecurityKey}`
- The request sends `UUID`, `deviceType`, `nativeToken`
- Authentication header: `X-HTTP-USER-TOKEN: %s`
- Login payload: `accessToken`, `platformId`, `platformType`
- Seven REST endpoints of the chat (`%s/user`, `%s/chat/message/%d`, …)
- **The AES key is chosen by the server** → whoever answers the handshake controls the channel
- To hijack the client a DNS redirect is enough: no patch of the binary

### Phase B — 8 October 2026: DNS solved, the client talks to us

**Why the guest's DNS never reached our server — two causes, in a row.**

1. **VirtualBox discards loopback DNS servers.** With the Windows DNS at `127.0.0.1`,
   `VBoxSVC.log` shows an **empty** list of name servers. You must
   put the **PC's LAN IP** (`192.168.1.185`): the server listens on `0.0.0.0:53` and
   VirtualBox accepts it (`name server 1: 192.168.1.185`). It reaches the guest via DHCP
   **only when the instance starts**: after the change, `quitall` and relaunch.
2. **The guest has opportunistic private DNS turned on** (`dumpsys connectivity`:
   `UsePrivateDns: true`). The guest's network lists `192.168.1.185, 8.8.8.8, 8.8.4.4`;
   `netd` finds that the two Google servers speak **DNS-over-TLS** and sends everything there on
   port 853. That is why the counters on port 53 stayed at zero, the answers
   carried `RRSIG` and no name reached the server. Remedy, now in
   `phaseb-guest.sh`: `settings put global private_dns_mode off`, REJECT on 853,
   DNAT of 53 towards the PC.

### The format of the master files — verified on the bench on 8 October 2026

**Transport.** A master file is a normal HTTP response with Content-Type
`application/octet-stream` (or `application/encoded-json`), decoded as:

```
body → curl_easy_unescape → base64Decode → AES-256-CBC (key, zero IV, PKCS#7) → JSON
```

- AES-256-CBC, zero IV, PKCS#7 padding. **The key is the 32 bytes of the string
  `key`** of the response to action 27, as they are;
- it is the same scheme as the session channel, only in the opposite direction;
- `md5` = **hexadecimal MD5 of the HTTP body as it arrives** (i.e. of the Base64). With
  this rule the client accepts the file, so the hypothesis holds.


**Successful test.** The server serves the tables it finds in `server/master_data/<name>.json`
(folder not versioned), with a stable key derived from the name. With a single `misc.json`
containing `[]` and `KHUX_REVISION=1`: action 27 → `GET /master/misc` → «Complete», no
error, and **`files/m/m065.jpg`** appears in the guest (`misc` is table 65 of the loader).
The client keeps the tables in its own cache format.

### The content of the master tables — derived and verified on 8 October 2026

**The shape.** The decrypted JSON of a table is an **array of rows**. If a row is
not valid, the table fails with **error 3** and the download stops.

**The types.** Each field has a fixed type: int32, int64, string (with a maximum length) or
array with a limit `n < N`. **Every field is mandatory**: if it is missing, the row is
rejected. Extra keys are ignored. Strings that are too long are truncated, not rejected;
arrays can be shorter than the limit, even empty.

The resulting schema is in **`recon/out/master_types_ww431.json`**, versioned because it describes
the interface, not the data. It contains 106 tables and **1,739 fields, all resolved**: 1,300
`int`, 165 `string`, 6 `int64`, 268 arrays (`int[N]`, `int64[N]`, `string(128)[3]`…).
No booleans or decimals: even the `valid*` flags are integers.

Examples:

```
misc       miscId int, value int
badstatus  badstatusId int, name string(64), iconId int, effect int, target int, power int[2]
world      …, partsId string(128)[3], xPostion int[3], yPostion int[3]
```

The server checks every `master_data/<name>.json` against the schema and **does not serve** the
tables that do not pass. With `KHUX_MASTER_SERVE_INVALID=1` it serves them anyway, for
tests.

**Verification on the bench.** There are two tests.
- *Positive*: `misc`, `badstatus` and `world` with one valid row each, revision 2. The
  client downloads all three, shows «Complete» and saves `m034`, `m065`, `m079`

- *Negative*: `misc` with `"value":"0"` (string instead of int), revision 3. It shows
  «**Master data error. (200 ERROR)**» at 33.3%, `badstatus` is no longer requested and
  `m065` stays the old one.

The schema is therefore confirmed in both directions.

### The resource download protocol — derived and tested on 8 October 2026

**Who starts it and when.** At startup the client decides what to download:
- **master data** (action 27) if the local master revision differs from the
  server's;
- **resources** (action 28) if the resource revision differs, **but only if the
  player is not new and has finished the tutorial**. The first piece of data is
  `systemLogin.newcomerKhux`, the second `isFinished` of the tutorial state.

A new player therefore does not download resources at startup: they do the tutorial with the graphics
already installed, i.e. APK **and OBB**. That is why the first crash after the
name registration (`AvatarEditAnim`) cannot be solved from the server: for a new
player **the OBBs are indispensable**.

**The requests.**

| Action | Body |
|---|---|
| 27 `GET /system/master/20200423` | `revision`, `commonRevision` |
| **28 `GET /system/resource`** | `revision` (local resources), `resoMode` |
| 29 `GET /system/resourceEv` | `resourceIds` |
| 242 `PUT /system/resourcesize/20200423` | `resoMode`, `masterRevision`, … |
| 256 / 257 / 258, the same for Dark Road | |

**The existing player goes through two other calls**, now in the server:
- `POST /khux/login` (action 252): `{gameLogin: {acquirableLoginBonus: bool}}`;
- `GET /tutorial/status` (69/70, at the root of the response): `phase` (uint),
  `popupFlag` (uint64), `isFinished` (uint), `acquireTutorialJewel` (bool).

**The response to `/system/resource`**:

```json
{ "resource": { "mode": 1, "minVersion": 1,
    "versions": [ { "data":  [ {"url": "…", "md5": "…", "size": 123} ],
                    "index": [ {"url": "…", "md5": "…", "size": 45} ] } ] } }
```

- `mode`: 0 = nothing, 1 = full (deletes and rewrites the package), 2 = incremental
  (checks the current size and appends);
- the i-th version is `minVersion + i`;
- each file wants `url` and `md5` as non-empty strings and `size` > 0;
- `/system/resourceEv`: array `resourceEv` of
  `{resourceId (uint), versions}`.

**The download** accepts a file only
if three conditions hold together:
- the body is `size` long;
- the hexadecimal MD5 of the body is `md5`;
- the Content-Type contains `application/octet-stream`.

It caches it under an obfuscated name; the cache redoes the same check.

**The installation** (when the queue is finished):
- the `data` files are concatenated into **`files/r/misc.mp4`** (Dark Road:
  `r/.misc.mp4`; event resources: own name + `.mp4`), possibly split into
  parts `%s.%d`;
- the `index` files of the latest version are concatenated into a temporary `misc.wav`,
  then renamed **`r/misc.png`**;
- finally the client reopens the index and requires, in order:
  1. a record named **`/`** (the index);
  2. an **`md5`** record, 32 long once decrypted with the session key (below);
  3. optionally, a **`size`** record with the package size in decimal,
     equal to the sum of the `data`.

  If something does not add up, «**Save error. Please check the storage space on your
  device.**» appears.

The downloaded resources are therefore **packages in the same format as those of the APK**, which `files/r/`
replaces. The CDN index however also had the `md5` and `size` records.

**Test on the bench** (`KHUX_NEWCOMER=0`, revision 7). The recorded flow is:

```
/system/status, /login/token, /session, /system/login, /system/coppa,
/khux/login, /tutorial/status, resourcesize ×4, Download →
/system/master + 106 tables → GET /system/resource {"revision":0,"resoMode":0}
→ GET /resource/1/data/… → GET /resource/1/index/…
```

- The files arrive intact (MD5s compared in the guest) and become `r/misc.mp4` and
  `r/misc.png`.
- With random bytes, and also with the `misc.mp4`/`misc.png` pair from the APK, it ends in
  «Save error», as expected: the APK's index lacks the `md5` and `size` records.
- The protocol is therefore verified up to the index check. To get past it
  the original CDN indexes are needed, or deriving the key of the `md5` records
  and building one. **Done: see below.**

**The key of the `md5`/`size` records is delivered by the server**: it is the
**fourth element** of the **`data`** field of `/system/login` (8 + 32 + 32 + 32 bytes,
each element in Base64).

So the original server distributed the key of the resource indexes to the clients.
Ours derives it in a stable way (`sha256("khux-resource-index")`, or
`KHUX_RESOURCE_KEY` in hexadecimal) and puts it in `data[3]`.

The record of the APK's `misc.png` is called precisely **`/`**. A private tool builds the
downloadable index: the starting index (the `/` record), followed by the `md5` record
(hexadecimal MD5 of the package) and `size` (its size), encrypted like the originals with the
session key. The content of `md5` is not compared with anything (it is enough that it is 32
long); `size`, if present, must equal the sum of the `data`.

**Verified on the bench.** I served as version 1 the APK's `misc.mp4` +
an index built this way: **no more «Save error»**, so the index is accepted and
the installation completes. Right after, the game crashes (a garbage pointer), without
other requests to the server. It is the step after the download and no longer
concerns the protocol: the test package is just a copy of the APK's,
and the scene that follows wants real resources and user data.

**The crash after the installation is tied only to that start** (in all likelihood an
object freed after the remounting of the packages). On the next restart the client declares
`resourceRevision: 1`, so the installation was recorded, and it no longer
crashes. It asked to download again, however, because the server declared `versionRes = 7`.

Now `ret.versionRes`/`versionResLow` are **the latest version present in
`resource_data`** (0 if none). With consistent revisions the existing player
goes on beyond the download:

```
… /khux/login, /tutorial/status, PUT /user/awakening, GET /user  →  «200 ERROR :1»
```

`GET /user` (action 1) wants the complete player data: it is the
next chapter.

### The APK's asset packages — read on 8 October 2026

The APK's assets (`misc.mp4`, `extra.mp4`, `aliud.png`, …) are neither videos nor images:
they are packages of encrypted records (the decoding tools are kept private). The file names
are in the **index**, the `.png` of the same name (`misc.mp4` → `misc.png`). Content of `misc.mp4`: 2,831 files — 2,442 texts (`text/`), 165 `lwf/`
animations, 152 `cocostudio/` layouts, interface images, shaders, audio, and two folders
that matter:

- **`json/server_api.json`** — the **complete table of the client's 321 actions**.
  The action ID is the index in the `actions` array; each entry has `path` and `method`
  (0 GET, 1 POST, 2 PUT). Verified on all the actions seen on the network: 0
  `/system/status`, 26 `/system/coppa`, 27 `/system/master/20200423`, 242
  `/system/resourcesize/20200423`, 251 `/system/login`. **It is the whole REST surface**,
  which until now we reconstructed one call at a time;
- **`json/server_config.json`** — `serverURLDomain` (`https://api-s.sp.kingdomhearts.com`)
  and the three strings of `systemStatusUpdate*` (the key for the encrypted URL of
  `/system/status`);
- **`info/`** — `version` 4.3.1, `build`, `commit`, `lang`, `dark_resource` 10, and:
  - `info/tutorial_master` = **`85883`**: not a master, but the **revision number**
    of the tutorial data;
  - `info/obb/main` and `info/obb/patch`: the **MD5s of two OBB files**, the Google Play
    expansion packages, which **are not in the APK**. In all likelihood the tutorial
    master data (and many resources) are there.

The extracted files stay in `D:\Progetto_Restauro_KH_UX\assets431\` (Square Enix data:
they do not go into the repository).

**Other download requests** not yet seen on the network carry `revision` (probably the
resources), `resourceIds`, `notUpdate`, and the revisions without `resoMode`.

**In all responses `maintenance` must be omitted.** The client checks that its JSON
type is null; even `0` counts as active maintenance and leads to the popup with `viewUrl`.
The old server sent `maintenance: 0`: it was wrong.

**The encrypted channel works with our key.** From step 4 the body is a form with
a single field, `v=<base64>`, and `<base64>` is **AES-256-CBC of the JSON, zero IV, without
inner Base64** (strategy `zero+noInnerB64` of `khux-codec.js`). The server now removes
the `v=` wrapper and logs the decrypted JSON. The first one, from `/system/login`:

```json
{"length":<bytes>,"digest":"<32 hex digits>","ruv":<int>,
 "deviceType":2,"systemVersion":"28","appVersion":"4.3.1"}
```

`length` is the size of the client library: `digest` is in all
likelihood its MD5, i.e. an integrity check of the client done **by the server**. For
us it is enough to accept it. Every game request also carries the headers
`X-Sqex-Hole-Retry` and `X-Sqex-Hole-Nsid`.

**The game responses go in clear text.** The client
chooses based on the Content-Type, searched as a **substring**: `application/json` or
`text/javascript` → direct parse; `application/encoded-json` or `application/octet-stream`
→ decryption; anything else → transport error 2. Our
`application/json; charset=utf-8` is fine: encryption is only needed for requests.

**The `ret` wrapper, common to all game responses.** The client reads the fields in this order
and at the first wrong JSON type discards the response: error 2, which on screen becomes
`200 ERROR :<action>`.

| Field | Type |
|---|---|
| `isMaintenance`, `isPhotonMaintenance`, `isKhuxMaintenance`, `isDarkMaintenance`, `sessionTO` | bool |
| `isNewDayPeriod` | int |
| `isRetry` | bool |
| `versionApp` | string — compared with the app version |
| `versionRes`, `versionResLow`, `versionDat`, `commonVersionDat`, `darkVersionRes`, `darkVersionDat`, `functionFlags` | int |
| `serverTime` | string `YYYY-MM-DD HH:MM:SS` (year ≥ 1000) |
| `error` (+ `viewUrl`), `isCommunicationMaintenance` | optional |

**The per-action check.** Besides `ret`, each of the 320 actions expects its own fields; if one
is missing or has the wrong type → error 2.

**Response to `/system/login` (action 251).** Besides `ret`:
- `systemLogin`: `{"newcomerKhux": bool, "newcomerDark": bool}`;
- `data`: array of **at least 4 Base64 strings**, of **8, 32, 32 and 32 bytes**. They look like a
  seed and three 256-bit keys; what they are for is not yet known. The server generates them
  randomly, stable for the lifetime of the process;
- 21 link strings: `support`, `register`, `update`, `help`, `staff`,
  `agreement`, `license`, `shikin`, `tokutei`, `store`, `odds`, `petOdds`, `appUpdate`,
  `officialSite`, `officialTwitter`, `movie`, `beginnersGuide`, `passiveSettingList`,
  `darkHelp`, `darkOdds`, `officialTwitterCustom`. Empty ones are enough.

**Response to `/system/coppa` (action 26).** Besides `ret`, `misc`: an object of **unsigned
integers** with keys `"116"`, `"804"`, `"900"`…`"907"`. Meaning
unknown; 0 is fine. The GETs carry the encrypted payload in the query (`?m=0&v=…`), and the server
now decrypts it like a body.

queries also appear (Microsoft, Discord, NVIDIA…) and those of LDPlayer (`ldmnq.com`,
`ldplayer.net`, `changzhi.top`). The Google apps in the guest fail with

## 4. Running

### Server

```
start-server.bat        (double click)
```

It detects the IP by itself (`server/lan-ip.ps1`) and starts HTTP, HTTPS and DNS on ports 80, 443 and
53. On Windows no administrator privileges are needed. You should see three listening lines.

### Network — the three stumbling blocks met on Windows

1. **Active VPNs** hijack the routing: the phone does not reach the PC. Turn them off.
2. **Port 53 may be taken** by Internet Connection Sharing, which
   Hyper-V and WSL start by themselves. `Stop-Service SharedAccess` as administrator;
   re-enable it afterwards with `Start-Service SharedAccess`.
3. **"Public" network profile**: the firewall blocks incoming connections. Rules are needed:
   ```powershell
   New-NetFirewallRule -DisplayName "KHUX server" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 80,443 -Profile Any
   New-NetFirewallRule -DisplayName "KHUX DNS" -Direction Inbound -Action Allow -Protocol UDP -LocalPort 53 -Profile Any
   ```

On a home network point 1 goes away and point 3 is unlikely to come up.

### Phone

1. Install the original APK (a repackaged one is refused by the protector)
2. Install `server/certs/ca.crt` as a **system CA certificate** (the app does not trust user CAs;
   on the LDPlayer bench `phaseb-guest.sh` does it)
3. Wi-Fi DNS → the PC's IP
4. Open the game and watch the console

### What to read in the console

| | |
|---|---|
| `[dns:dirottata]` | the client is resolving our hosts |
| `[dns]` | queries forwarded upstream — **this is where the real bootstrap host appears** |
| `[ok]` | the client accepted our responses |
| `[?]` | unknown endpoint, body already decrypted — **it is the material to collect** |

If you see DNS queries but no HTTP request: the client is contacting a host that we do not
hijack (add it to `KHUX_HIJACK`), or it rejects the certificate.
